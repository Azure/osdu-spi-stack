# ADR-015: Partition, Entitlements, and Legal Bootstrap via a Flux Helm Chart

## Context

OSDU's Azure provider needs three pieces of state in place before any record, schema, or entitlements operation can succeed against a fresh cluster:

1. **A partition record.** Every service resolves partition-specific backend config (Cosmos endpoint, Service Bus namespace, storage account, elastic credentials) by calling `partition-service`. Without a record, those lookups return nothing.
2. **Entitlements root groups.** Authorization calls look up the caller's appid in `users.data.root@{partition}...` and siblings. With an empty entitlements DB every call returns 401, regardless of which identity the caller holds. System-schema writes authorize separately, against `service.system-schema-service.editors` in the partition the schema service is configured with; the Azure provider's tenant-provisioning does not create that group.
3. **A default legal tag.** Every stored record carries a legal tag, and legal validates a tag's `countryOfOrigin` against a country-of-origin catalog blob it reads from its configuration container. Without a compliant tag, ingestion and the fork acceptance suites have nothing to reference.

All three are mechanical, one-shot operations that have to happen exactly once per partition per environment. The same structural problem ADR-013 solved for schema-load applies here, scaled to an additional admin concern: per-partition identity provisioning.

## Decision

Bootstrap partitions, entitlements, and legal tags with a Flux-managed Helm chart that renders four one-shot Jobs per partition:

- `partition-init-{partition}-{hash}` POSTs the partition record to `partition-service`, or PATCHes the same properties onto a record that already exists. The hash covers the record body and the Job spec, so a record or Job change renames the Job and Helm runs it again on an environment that already has a partition. The record carries the OSDU workload identity's client id as `app-dev-sp-username`, which core-lib-azure reads into `TenantInfo.serviceAccount`, and as `serviceAccount`, the key the community acceptance suites read; the CLI supplies it through `spi-init-values`.
- `entitlements-init-{partition}-{hash}` POSTs `tenant-provisioning` so entitlements creates root groups with the caller's appid as OWNER. In the primary partition, the first in the list and the only one that hosts the system database, the Job then creates each group in the chart's `systemGroups`, which holds `service.system-schema-service.editors`. The OSDU identity creates the group and becomes its OWNER, which is the membership the schema-load Job presents. The schema release sets `AZURE_SYSTEM_AUTHORIZATIONPARTITION` from `PRIMARY_PARTITION` in `osdu-config`, so the check and the group meet in one partition; an unset value falls back to `system`, which no environment provisions, and the write fails closed.
- `legal-init-{partition}-{hash}` stages the country-of-origin catalog into the partition's `legal-service-azure-configuration` container and POSTs the `{partition}-demo-legaltag` default tag.
- `entitlements-members-{partition}-{hash}` adds the environment's deploy identity (ADR-032) to `users`, `users.datalake.ops`, `users.datalake.admins`, `users.data.root`, `users.datalake.delegation`, and `users.datalake.impersonation`, so fork CI has a caller entitlements recognizes and the OSDU identity can act for it during ingestion (ADR-044). The Job adds the member identity to `users`, every `service.<name>.user` group the listing carries, and `service.storage.admin`, so fork CI also has a caller who may use each service but is no data manager. In the primary partition the deploy identity also joins the `systemGroups`, since the schema acceptance and integration suites both write system schemas as that caller; the member identity does not. Storage defines no `.user` group, and its acceptance suite requires that caller to hold `service.storage.admin`; a listing without that group fails the Job before any write. The Azure provider's tenant-provisioning creates none of the impersonation groups, so the Job first creates `users.datalake.delegation` and `users.datalake.impersonation` when they are absent. Their creator is the OSDU identity and becomes OWNER, which already puts that identity in delegation; no new delegator grant is needed for DAGs. The hash is over both member lists and a seed generation the chart and CLI both carry: a Job's pod template is immutable, so a changed list, or a bump for what the Job seeds or for a change to its spec, renders a new Job and Helm prunes the old one.

Shape:

- Chart `software/charts/osdu-spi-init/` with `partition-record.yaml`, `scripts.yaml`, `partition-init.yaml`, `entitlements-init.yaml`, `legal-init.yaml`, `entitlements-members.yaml` templates. The four Job templates all loop over `.Values.partitions` so a multi-partition deploy renders one Job per partition with no extra manifests.
- A Job's spec is immutable, so Helm cannot patch a changed Job in place and the upgrade fails. The `entitlements-init` and `legal-init` hashes cover the Job spec for that reason; the members Job keeps a name the CLI computes, so its spec changes ride on the seed generation. `spi info` finds `legal-init` by its component and partition labels. A cluster test installs the base revision's chart and upgrades it to the working tree.
- Members generation 6 adds the system groups for the deploy identity. Its 1620-second request budget includes the additional write/read pair; the 2520-second Job deadline exceeds the computed 2465-second worst case. The members HelmRelease waits 45 minutes, and its Kustomization waits 50.
- Every Job carries a `podFailurePolicy` that ignores exit code 126 from any container. Istio's `istio-validation` init container exits 126 while a new node's CNI is still starting, before the Job's script runs, and each such failure would otherwise spend `backoffLimit: 2`. Istio injects the container at admission, so a rule cannot name it: the API server rejects a `containerName` absent from the pod template. The scripts exit 0 or 1, never 126, and `activeDeadlineSeconds` bounds a CNI that never comes up.
- All four Jobs share the `workload-identity-sa` ServiceAccount (ADR-005) and the chart's `auth.py`, which exchanges the federated token at the v1.0 endpoint so the token carries `appid`. The caller's appid is the OSDU UAMI client id, which is what `partition-azure` stores as `TenantInfo.service-account` and what entitlements-azure authorizes as bootstrap admin on an empty DB.
- Partition list is injected via a `spi-init-values` ConfigMap the CLI writes (driven by `--partition` flags). The HelmRelease consumes it with `valuesFrom`, so adding a partition is a CLI argument change, not a Git edit. The ConfigMap carries Flux's watch label, so a changed partition list reconciles the init, legal, and members releases at once instead of at their 30-minute interval. The same ConfigMap carries `entitlementsMembers`, the deploy identity's client id, written by `spi up` and refreshed by `spi reconcile` from `spi-cluster-config`; no members Job renders while the list is empty.
- Partition record values use bare Key Vault secret suffixes (`cosmos-endpoint`, `sb-namespace`, etc.), not partition-prefixed names. `partition-azure` auto-prefixes the partition id onto every `sensitive: true` value at write time, so embedding the prefix in the chart double-prefixes the stored value and breaks downstream service lookups.
- New Kustomization `spi-osdu-init` at `software/stacks/osdu/init/`, wired into the core profile as Layer 5a (after `spi-osdu-services`, before `spi-osdu-schema-load`) per ADR-007. `schema-load` depends on `spi-osdu-init` so the schema POSTs see a tenant that is already provisioned.
- `partition-init` and `entitlements-init` start in parallel within the gating release. An unauthenticated partition lookup cannot prove that the record exists because partition returns 403 both before and after creation, so `entitlements-init` retries tenant provisioning while entitlements reports `Invalid data partition id`. This covers partition creation and entitlements cache lag without relying on Job ordering. The members Job retries the same response on any call for up to ten minutes, since each entitlements replica fills its partition cache on its own. `legal-init` is downstream of both: its Kustomization depends on `spi-osdu-init`, whose health check holds until helm has waited out those Jobs. Its gates therefore cover cache lag and re-runs, not ordering, and it still waits for an authenticated `GET /legaltags` to return 200 because entitlements and legal each cache their view of the groups.
- A Job's success proves only that the replicas serving its own requests know the partition. Entitlements' `AuthorizationFilter` answers 403 `Invalid data partition id` from the replica's own tenant set, and legal's `LegalTagRepositoryFactoryImpl` answers 403 from the same core-lib-azure tenant factory; a lagging entitlements replica kept rejecting a new partition for 4 to 12 minutes after the members Job succeeded. `spi up` therefore writes `DATA_PARTITIONS_HASH`, a sha256 over the sorted partition list, to the `spi-partitions` ConfigMap right after `spi-init-values`. `spi-osdu-services` substitutes it into the entitlements, legal, storage, and search releases as `partitionsHash`, which the service chart stamps on the pod template as `osdu.spi/partitions-hash`, so a changed list rolls those Deployments and each new pod reads the partition list after the change. Storage and search resolve tenants through the same factory; their lag after a partition add is unmeasured, and they roll with the other two. The hash cannot ride in `spi-init-values`: Flux rejects a substitution source whose keys, such as `values.yaml`, are not variable names. `spi-partitions` carries the watch label and is optional to the Kustomization, so an environment without it renders no annotation.
- `legal-init` resolves the partition's blob endpoint from the `{partition}-storage-account-blob-endpoint` Key Vault secret and PUTs the catalog into the container `partition.bicep` creates. legal-azure resolves that container from its own `AZURE_STORAGE_CONTAINER_NAME` env plus the partition record, so there is no bucket property to PATCH onto the partition and no Azure equivalent of that upstream step. The catalog overrides entries in legal's `DefaultCountryCode.json` rather than replacing the list, and it must stay a superset of the legal acceptance suite's `TenantConfigTestingPurpose.json`: those tests create `MY` tags expecting 201, and the suite's own uploader skips a blob that already exists, so the staged file is what they read. The tag is the deliverable, so a failed catalog upload does not block it: the Job records `catalog_not_staged`, still POSTs the tag, and exits non-zero so the gap stays visible.
- `legal-init` prints one typed `legal-init outcome: <code>` line on every exit, so a failure is diagnosable from the Job log without re-running it. Seeding a legal tag is not a readiness gate: helm-controller waits for every Job in a release, so `legal-init` renders only in the separate `osdu-spi-legal` HelmRelease (same chart, `legalEnabled`/`coreEnabled` toggles) behind the non-gating `spi-osdu-legal` Kustomization at `software/stacks/osdu/legal/` (Layer 5c, `spi-stack.gating: "false"`, ADR-030), and `ready` and `seeded` stay separate signals.
- Idempotence: 201 from partition-service counts as success and 409 leads to a PATCH, which counts as success on 204; 200 and 409 from entitlements-tenant-provisioning count as success. A 403 `Invalid data partition id` from tenant provisioning is retried while the partition record and entitlements cache converge; other 403 responses fail immediately. The catalog upload overwrites. A 409 from legal-legaltags counts as success only once the existing tag is verified to be the one this Job would have created, since a taken name is not proof that bootstrap converged: `legal-init` compares the stored properties against the tag body and asks `legaltags:validate` for legal's own validity verdict, and a mismatch, an invalid tag, or a failed check exits `legal_tag_conflict`. No `ttlSecondsAfterFinished` (same rationale as ADR-013: Flux would re-create an auto-deleted Job and turn one-shot into periodic).

Rejected:

- **A dedicated `system` partition for the system-schema group.** Matches the community layout, but needs a partition record and its Cosmos, Service Bus, and storage wiring to hold one group.
- **Imperative CLI step.** Re-opens the problems ADR-011 and ADR-013 closed: hidden CLI dependency, no re-run from the cluster, invisible to `flux get kustomizations`.
- **Per-partition Flux Kustomization stamping.** One Kustomization per partition duplicates every wiring decision above. A single Kustomization holding a chart with a per-partition loop is the same outcome with less YAML.
- **Partition-prefixed values in the chart's `partition.json`.** Double-prefixes every stored value and surfaces as "Invalid data partition id" the first time a service dereferences the record. The bare-key pattern matches what `partition-azure` expects.
- **Service releases reading `spi-init-values` through `valuesFrom`.** Needs no second ConfigMap, but the shared service chart would parse the init chart's values shape, and a member list change would upgrade four service releases.
- **A bootstrap Job restarting the Deployments.** Orders the roll after `partition-init`, but the Job's identity would need to patch Deployments in `osdu`.

## Consequences

- Fresh deploy reaches a schema-loaded cluster with no CLI post-step and no manual entitlements provisioning.
- Multi-partition enables via `spi up --env dev1 --partition p1 --partition p2`; the chart renders one partition-init, one entitlements-init, one legal-init, and one entitlements-members Job per partition with no manifest changes.
- A partition change rolls entitlements, legal, storage, and search. The roll and `partition-init` start together, so a pod that reads the partition list before the record exists still lags until its own refresh; the members Job's ten-minute retry covers that window. The first `spi up` on an environment without `spi-partitions` rolls the four services once with an unchanged list.
- Four per-partition Key Vault secrets are declared in `partition.bicep` (`{p}-storage-account-blob-endpoint`, and `"DISABLED"` placeholders for `{p}-cosmos-connection`, `{p}-sb-connection`, `{p}-storage-account-key`) so the partition record resolves under Workload Identity without exposing real connection strings (ADR-023). The `{p}-sb-connection` placeholder leaves indexer-queue's community image unable to authenticate; the gap is covered in ADR-005.
- Manual re-run is `kubectl delete job -n osdu partition-init-{p}-{hash} entitlements-init-{p}-{hash}` followed by `flux reconcile kustomization spi-osdu-init`. Legal seeding re-runs on its own Kustomization: `kubectl delete job -n osdu legal-init-{p}-{hash}` followed by `flux reconcile kustomization spi-osdu-legal`; members seeding likewise with `entitlements-members-{p}-{hash}` and `spi-osdu-members`. A 409 on re-run is success for the entitlements and members Jobs, an update for the partition Job, and for legal once the existing tag verifies.
- The tag is published as `partitions[].legal_tag` in `spi info --json` (ADR-030) only after that partition's Job succeeds, so acceptance suites reference a tag the cluster is observed to hold rather than reconstructing the name or trusting a seed that never ran. The configured name stays visible as `legal_tag_desired`. Membership is published the same way as `entitlements_seeded.{partition}`, read from the Job whose name the current member list computes.
- System-schema write access is membership of `service.system-schema-service.editors` in the primary partition: the OSDU identity as OWNER and the deploy identity as member. Creating the group is part of the gating release, so a rejected create holds schema-load and every later layer. Only the primary partition's `entitlements-init` Job carries `SYSTEM_GROUPS`, so a change to `systemGroups` reruns that Job alone; the members Job name does not cover the list, so the same change needs a `membersGeneration` bump to seed the deploy identity. A schema image without the configurable authorization partition ignores both the variable and the group.
- Members seeding renders in its own non-gating `osdu-spi-members` release behind `spi-osdu-members`, like legal, so it never holds schema-load. Unlike legal, a failed members Job is a deployability blocker (`bootstrap_failed`, ADR-030): a fork cannot run a positive test until its deploy identity holds the root groups, and refusing the deploy names the cause instead of leaving the suite to fail on a 401.
- Reference data is not bootstrap: it loads after the environment is deployable, through `spi load` (ADR-040). The bootstrap seeds no people; a person joins through `spi users` (ADR-039).
