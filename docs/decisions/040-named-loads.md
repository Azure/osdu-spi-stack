# ADR-040: Named Loads Run Through the CLI and Publish Their State

## Context

Bootstrap leaves an environment with its shared schemas registered and no
records. The schema Job runs the loader paired with the schema service's
commit (ADR-013, ADR-033), but its result is a Kubernetes Job that
`spi info --json` does not report, and its re-run is a `kubectl delete`.
Reference data, the 80,103 records of 584 kinds in the data-definitions
repository, is loaded by nothing, so a search or indexer suite against a new
environment finds no records and nothing says why. No service builds that
payload, so it has no commit in common with one, and loading it takes long
enough that it cannot sit inside a Flux reconcile wait. ADR-015 rejects a CLI
step for bootstrap because bootstrap gates readiness; a load that runs after
the environment is deployable does not.

## Decision

A load is a named entry in a registry the stack version delivers, `spi load`
runs it, and `spi info --json` publishes its state in a `loads` block.

- **The registry belongs to the environment.**
  `software/stacks/osdu/init/load-registry.yaml` reaches the cluster as the
  ConfigMap `spi-load-registry` in `osdu`, generated by the `spi-osdu-init`
  Kustomization. `src/spi/loads.py` reads that copy and carries no dataset
  list, so a CLI and an environment of different versions agree on what a
  name means. An environment without the ConfigMap is refused.
- **`schemas` is the existing Job.** Its entry has `runner: flux`: the CLI
  reports the `schema-load` Job against the image lock and never creates it.
  `spi load --dataset schemas --force` deletes the Job and reconciles
  `spi-osdu-schema-load`.
- **`reference-data` is a Job the CLI creates.** `templates.load_job` renders
  one Job per partition, named `load-<dataset>-<partition>-<first 8 of the
  source commit>`, running `load_records.py` from the init chart's scripts
  ConfigMap as `workload-identity-sa`. The Job carries no TTL, as the
  bootstrap Jobs do not: it is the record.
- **The source is pinned by commit.** The registry names a data-definitions
  release and the commit its tag points to. The Job fetches the archive from
  community GitLab by commit and refuses one whose zip comment names another.
  Moving the pin is a reviewed change that ships in a stack release.
- **Reference data never runs ahead of the schemas.** Before any write the
  loader asks the schema service for each kind in the payload and fails with
  `schema_behind`, naming up to 20 kinds, when one is missing. `requires:
  [schemas]` in the registry refuses the load, exit 2, until the schema load is
  `complete` or `stale`.
- **The loader owns ACL and legal.** Each record gets the partition's
  `data.default.owners` and `data.default.viewers` groups and its seeded legal
  tag in place of what the manifest carries. Records are written in batches of
  500 with `skipdupes`; 200, 201, and 409 are success, and the Job fails when
  more than 1% of the records failed or a manifest does not parse.
- **A second run is decided by the newest Job** for the dataset and partition:
  none creates one, a running Job is waited on, a complete Job for the same
  source changes nothing, a complete Job for another source is replaced once
  the new one completes, and a failed Job is deleted and recreated. `--force`
  recreates a running or complete Job.
- **State is `absent`, `running`, `complete`, `stale`, or `failed`.** `stale`
  is a completed load whose source is not the one the registry now names. A
  load across partitions reports the weakest. Record counts come from the
  loader's outcome line, which `spi load` copies from the pod's termination
  message to the Job annotation `osdu.spi/outcome`.
- **A load never changes `ready` or `deployable`.** It runs after both, and a
  failure is reported in `loads` and by the command's exit code.

Rejected: build the reference values into the schema fork's loader image. The
pairing by commit comes free, but the schema build would fetch a second
upstream and an environment taking schema from the community image would get
no reference data.

Rejected: a Flux-managed, non-gating Job, as legal seeding is (ADR-015). It
runs without the CLI, but a pin change edits an immutable Job template and the
load would sit inside every reconcile wait.

Rejected: a ConfigMap as the state. It survives Job deletion, but the writer
would be the Job, through a ServiceAccount every OSDU service shares, or a
CLI that has to be watching when the Job ends.

Rejected: read the data-definitions release from the schema image. It needs a
label on the loader image and a stack that trusts it; the kind check gives the
same protection with no contract between repositories.

Rejected: manifest ingestion through the workflow service. It validates each
record against its schema and puts Airflow and the ingestion DAG in the path
of every rebuild.

## Consequences

- A fork's suite can require seeded data by reading `loads` instead of
  finding zero records.
- The archive is fetched from community GitLab on every Job run. An outage
  there fails the load and leaves the environment deployable. The commit
  pins the content but no digest verifies the bytes; a mirror is unbuilt.
- The kind check compares kind names and versions, not schema content, and
  accepts reference data older than the schemas.
- `complete` means the storage service accepted the records. The indexer may
  still be working through them.
- Deleting a load Job removes the fact while the records remain. `spi load`
  restores it, with every record skipped as a duplicate.
- Counts are empty when the pod was collected before any `spi load` run saw
  the finished Job.
- The fork deploy identity cannot create Jobs (ADR-032), so fork CI reads
  `loads` and cannot start a load.
- The loader holds one manifest in memory at a time and the largest is 76 MB
  of JSON, which is why the Job's memory limit is 2Gi where the bootstrap
  Jobs have 512Mi.
- A first load of the 80,103 records took 7 minutes on a core environment,
  5 of them in the loader, and a forced reload that skips every record took 3.
  The 7200 s Job deadline is headroom for a larger dataset, not a measured need.
- A load pod carries the mesh sidecar. On a node provisioned for it the
  sidecar's validation container can fail once before the loader starts;
  `backoffLimit: 2` retries the pod.
