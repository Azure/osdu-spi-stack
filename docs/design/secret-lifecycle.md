# Secret lifecycle

The CLI generates middleware passwords and preserves them in
`osdu-flux/spi-secrets`. It copies those values into Kubernetes Secrets and,
for Redis and Elasticsearch consumers, into Key Vault. Bicep separately writes
Azure-derived configuration and compatibility placeholders to Key Vault.

Workload Identity provides token-based access without a stored UAMI client
secret. It does not eliminate the credential inventory below.

## Writers and consumers

| State | Writer | Consumers |
|---|---|---|
| `osdu-flux/spi-secrets` | CLI, generated on first bootstrap and reused on subsequent runs | CLI bootstrap and Key Vault writes |
| Middleware Secrets in `platform` | CLI, copied from the seed | Elasticsearch, Redis, PostgreSQL, Airflow |
| Elasticsearch Secrets in `osdu` | CLI, copied from the seed | Service configurations that reference those Secrets |
| Azure metadata and `DISABLED` placeholders in Key Vault | Bicep | Azure-provider services using their configured Key Vault access |
| Redis and per-partition Elasticsearch values in Key Vault | CLI after Flux activation | OSDU services reading shared or partition-prefixed values |
| TLS certificates and CA material | cert-manager and ECK; trust-manager distributes CA copies | Gateways, middleware, and Java truststore initialization |

Kubernetes ConfigMaps such as `osdu-config` carry endpoints and IDs, not the
middleware passwords. Short-lived access tokens are obtained at runtime; see
[Workload Identity](workload-identity.md).

## Middleware credential seed

`get_or_create_seed()` in `secrets.py` reads `spi-secrets`. If a required field
is missing, it generates a password for that field and persists the result.
Existing complete seeds are reused. Passwords are random, not derived from the
environment name.
Airflow's Fernet key has a separate generator: URL-safe base64 encoding of
32 random bytes, not the alphanumeric password format.

`ensure_secrets()` then applies these copies:

| Kubernetes Secret | Key or contents |
|---|---|
| `platform/elasticsearch-es-elastic-user` | `elastic` password |
| `platform/redis-credentials` | `password` |
| `platform/postgresql-superuser-credentials` | PostgreSQL administrator username/password |
| `platform/postgresql-airflow-credentials` | Airflow database username/password |
| `platform/airflow-metadata-secret` | PostgreSQL connection string built from the seed |
| `platform/airflow-api-credentials` | Airflow administrator password, API secret, JWT secret, and Fernet key |
| `osdu/indexer-elastic-secret`, `osdu/search-elastic-secret` | Elasticsearch username/password |

The Redis chart explicitly uses `existingSecret: redis-credentials`. CNPG
references the CLI-created PostgreSQL Secrets, and Airflow reads
`airflow-metadata-secret`. These are not passwords generated by the Helm chart
or database operator during the normal bootstrap path.

The seed is important state. Deleting it can cause a later `spi up` to generate
different passwords while existing databases still hold the previous ones.
Kubernetes Secrets are also not encrypted merely because their YAML values
are base64-encoded.

## Key Vault values

Bicep and the CLI write different values, at different points in deployment.

### Azure-derived values

`main.bicep` and its modules declare metadata such as `tenant-id`,
`keyvault-uri`, `system-storage`, `graph-db-endpoint`, `{p}-cosmos-endpoint`,
`{p}-storage`, and `{p}-sb-namespace`.

`{p}-cosmos-primary-key`, `{p}-cosmos-connection`, `{p}-sb-connection`, and
`{p}-storage-account-key` contain `DISABLED`. The primary partition also writes
`system-cosmos-endpoint` and disabled system key/connection placeholders.
`graph-db-primary-key` is not written.

These are compatibility names, not fallback credentials. Cosmos and Service
Bus disable local authentication, and Storage disables shared-key access.
Community clients that require keys or SAS fail against these placeholders;
they need Workload-Identity-capable images, not a secret replacement.

The deployment is not transactional. If one secret write fails, resources and
earlier writes can remain. Reapplying the same value can also create Key Vault
secret versions; do not equate a repeat deployment with a guaranteed no-op.

### Seed-derived values

After activating Flux, `deploy.py` writes:

| Key Vault secret | Source |
|---|---|
| `redis-hostname`, `redis-password` | In-cluster hostname and the seed's Redis password |
| `{p}-elastic-endpoint`, `{p}-elastic-username`, `{p}-elastic-password` | Shared Elasticsearch endpoint, `elastic` username, and seed password |
| `tbl-storage-endpoint` | Common Storage account name from Bicep outputs |

All values are known before middleware readiness. The CLI does not read
operator-generated passwords after startup. It retries the first write for a
limited time if the deployer's Key Vault RBAC assignment has not propagated;
other write failures stop deployment.

Re-running `spi up` repeats these writes. `spi reconcile --refresh-images`
does not: that command only updates image selection and requests reconciliation.

### Partition secret lookup

For partition properties marked `sensitive: true`, the Azure provider prefixes
the partition ID when resolving the Key Vault secret. The partition record
therefore uses a bare suffix:

```json
{
  "value": "cosmos-endpoint",
  "sensitive": true
}
```

For partition `opendes`, that property resolves `opendes-cosmos-endpoint`.
Putting `opendes-cosmos-endpoint` into the record itself would double the
prefix. The record template is in the
[initialization chart](../../software/charts/osdu-spi-init/templates/partition-record.yaml).

## Inspecting ownership without exposing values

These commands show the relevant objects and Key Vault secret names without
requesting secret contents. Replace `<vault-name>` with the environment's vault:

```bash
kubectl describe secret spi-secrets -n osdu-flux
kubectl get secret redis-credentials elasticsearch-es-elastic-user -n platform
kubectl get helmrelease redis -n osdu-flux -o yaml
az keyvault secret list --vault-name <vault-name> \
  --query '[].{name:name,enabled:attributes.enabled}' --output table
```

Avoid attaching `kubectl get secret -o yaml` or `spi info --show-secrets` output
to issues or PRs. They expose credential material.

## Rotation is not automated

There is no supported end-to-end password-rotation command in the CLI. Do not
delete a chart Secret and assume reconciliation will rotate the password:
Redis consumes the existing CLI-owned Secret, and the credential seed remains
the value reused by later deployments.

A rotation procedure would need to coordinate the persistent seed, database
authentication state, Kubernetes copies, Key Vault copies, and consumers that
cache credentials. It also needs a rollback plan for a partially updated system.
Until that procedure exists, treat rotation as planned maintenance rather than
an image refresh or a generic pod restart.

## CA distribution and Java truststores

cert-manager issues Redis TLS material; ECK manages Elasticsearch HTTP
certificates. trust-manager reads their CA Secrets from `platform` and writes
`redis-ca-cert` and `elastic-ca-cert` in `osdu`, as declared by the Bundle
resources.

The service chart's `import-ca-certs` init container imports these CAs into a
Java truststore in an `emptyDir` volume. Updating a Bundle refreshes the target
Secret, but **does not rerun an existing pod's init container**. CA rotation
therefore needs a plan to recreate affected pods and confirm they trust the new
chain; Secret synchronization alone is not end-to-end truststore rotation.

The bootstrap Kustomization also applies a Redis DestinationRule that disables
Istio TLS origination for that destination. The application still uses native
Redis TLS; disabling mesh TLS is not disabling Redis encryption.
